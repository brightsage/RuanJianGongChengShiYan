# 数据采集与接入 / 学生画像 模块说明

本文档对应 `feature/WeiEnRui` 分支。两个模块已经从“只有数据层”推进到**可运行的 HTTP 接口**：数据源、字段映射、导入任务、导入执行、原始记录、学生读模型、指标、标签、画像快照和 HTML 报告都已接通。`tests/module_api_test.cpp` 和 `tests/http_smoke.py` 覆盖了完整业务流。

## 2. 分层结构

```
HTTP 请求
   │
   ▼
module.cpp                      只做模块注册、路由登记、参数转发
   │
   ▼
service.cpp                     参数校验、用例编排、导入校验、标签计算
   │
   ▼
repository.hpp                  持久化接口（可替换实现、方便测试）
   │
   ▼
sqlite_repository.cpp           SQL 与表结构（文件名为兼容保留，底层是 MySQL）
   │
   ▼
platform::Database              MySQL 连接、参数绑定、事务
```

约定：

- `module.cpp` 不写业务规则，只把请求转给 service。
- `service.cpp` 负责“能不能导入”“标签是否命中”“报告怎么生成”。
- `repository` 只负责读写，不判断业务。
- HTTP 请求/响应仍然使用 `platform::Request` / `platform::Response`。

## 3. 数据采集与接入模块（M1）

路由前缀：`/api/modules/data-ingestion`。

### 3.1 接口

| 用例 | 方法与路径（相对前缀） | 说明 |
| --- | --- | --- |
| UC-DC-01 登记数据源 | `POST /sources` | 名称、类型、接入方式、责任人；名称重复返回 409 |
| 查询数据源 | `GET /sources`、`GET /sources/:id` | 列表/详情 |
| UC-DC-07 维护字段映射 | `PUT /sources/:id/mappings` | 整体替换；支持 `trim`、`lower`、`upper`、`number` |
| UC-DC-02 配置导入任务 | `POST /tasks` | 数据源、导入方式、校验规则 |
| 查询导入任务 | `GET /tasks`、`GET /tasks/:id` | 列表/详情 |
| UC-DC-06 调度采集任务 | `PUT /tasks/:id/schedule` | 保存导入方式与调度表达式，暂不启动定时器 |
| UC-DC-03 执行导入任务 | `POST /tasks/:id/run` | 逐行映射、校验、写入原始记录；支持 `idempotency_key` |
| UC-DC-04 查看导入结果 | `GET /runs/:id`、`GET /runs/:id/records?failed=1` | 汇总与失败明细 |
| UC-DC-03 重试失败记录 | `POST /runs/:id/retry` | 只重跑失败行；可带修正后的 `records` 和 `idempotency_key` |
| UC-DC-05 接收外部数据推送 | `POST /push` | 按 `task_id` 或 `source_id` 执行；没有推送任务时自动创建；支持 `idempotency_key` |

导入请求示例：

```json
{
  "records": [
    {"xh": " 2023001 ", "cj": "92"},
    {"xh": "", "cj": "50"}
  ]
}
```

返回：

```json
{
  "run": {"id": 1, "task_id": 1, "status": "partial",
          "total_count": 2, "success_count": 1, "failure_count": 1},
  "failures": [
    {"source_row_no": 2, "valid": false, "error_reason": "missing required field 'student_id'"}
  ]
}
```

执行导入或外部推送时可以带 `idempotency_key`：同一个任务重复提交同一个 key 会直接返回第一次的执行结果，不会重复生成 `ing_raw_record`。失败记录用 `POST /runs/:id/retry` 重跑；不带 `records` 时重跑原始失败行，带 `records` 时用修正后的数据。

### 3.2 映射与校验规则

字段映射把源字段转成标准字段：

```json
[
  {"source_field": "xh", "standard_field": "student_id", "transform_expr": "trim"},
  {"source_field": "cj", "standard_field": "score", "transform_expr": "number"}
]
```

任务校验规则支持：

```json
{
  "required": ["student_id", "score"],
  "types": {"student_id": "string", "score": "number"},
  "ranges": {"score": {"min": 0, "max": 100}}
}
```

- `required`：字段缺失、为 null 或空字符串都算失败。
- `types`：`number` / `string` / `boolean`。
- `ranges`：只对数字字段生效，支持 `min`、`max`。

### 3.3 表结构

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `ing_data_source` | `name`、`kind`、`access_mode`、`owner` | 数据源登记，名称唯一 |
| `ing_field_mapping` | `data_source_id`、`source_field`、`standard_field`、`transform_expr` | 源字段到标准字段 |
| `ing_import_task` | `data_source_id`、`import_mode`、`schedule_expr`、`validation_rules`、`status` | 任务配置 |
| `ing_import_run` | `task_id`、`status`、`total_count`、`success_count`、`failure_count` | 每次执行结果 |
| `ing_raw_record` | `run_id`、`source_row_no`、`payload`、`valid`、`error_reason` | 原始记录与失败原因 |

约束：

- `ing_raw_record` 对 `(run_id, source_row_no)` 唯一。
- 外键开启，删除数据源会级联删除映射。
- `replace_field_mappings` 在一个事务里完成“删旧 + 写新”。

## 4. 学生画像模块（M3）

路由前缀：`/api/modules/student-profile`。

### 4.1 接口

| 用例 | 方法与路径（相对前缀） | 说明 |
| --- | --- | --- |
| 同步学生读模型 | `POST /students` | 由治理模块调用；`student_id` 已存在时更新 |
| UC-SP-07 查看学生画像详情 | `GET /students?major=&class=` | 按专业/班级过滤 |
| UC-SP-03 查看个人画像 | `GET /students/:id?term=` | 学生、指标、标签、快照 |
| 同步指标值 | `POST /metrics` | 由治理模块调用；按学生+指标+学期 upsert |
| UC-SP-01 维护标签体系 | `POST /tags`、`GET /tags` | 标签定义与规则 |
| UC-SP-02 计算画像指标 | `POST /recalculate` | 单个学生：指标 → 标签 → 快照 |
| UC-SP-02 批量计算 | `POST /recalculate/batch` | 按学期批量重算；不传 `student_ids` 时计算全部学生 |
| UC-SP-04 查看标签依据 | `GET /students/:id/tags/:code/evidence?term=` | 规则、取到的指标值、来源 |
| UC-SP-05 对比画像 | `GET /students/:id/compare?peer=&term=` | 指标差值与标签差异 |
| UC-SP-06 导出画像报告 | `GET /students/:id/report?term=` | 返回 HTML；默认页面展示，加 `download=1` 下载 |

批量计算示例：

```json
{"term": "2026-fall", "student_ids": ["2023001", "2023002"]}
```

不传 `student_ids` 时会对全部学生重算，返回每个学生的指标数、标签数和标签代码。标签结果按 `(student_id, tag_code, term)` 唯一，重算某一学期不会覆盖其它学期。

标签规则示例：

```json
{"metric": "comprehensive_score", "operator": ">=", "value": 90}
```

支持 `>=`、`>`、`<=`、`<`、`==`、`!=`、`between`。`between` 使用 `min`/`max`：

```json
{"metric": "comprehensive_score", "operator": "between", "min": 80, "max": 90}
```

画像查询返回：

```json
{
  "student": {"student_id": "2023001", "name": "张三", "major": "软件工程"},
  "term": "2026-fall",
  "metrics": [{"metric_code": "comprehensive_score", "value": 95, "unit": "分"}],
  "tags": [
    {"code": "score_excellent", "name": "成绩优秀",
     "evidence": {"metric": "comprehensive_score", "value": 95,
                  "rule": {"metric": "comprehensive_score", "operator": ">=", "value": 90}}}
  ],
  "snapshot": {"term": "2026-fall", "payload": {"metrics": {}, "tags": []}}
}
```

### 4.2 表结构

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `sp_student` | `student_id`、`name`、`major`、`class_name`、`grade` | 学生读模型，主数据由治理模块负责 |
| `sp_metric_value` | `student_id`、`metric_code`、`term`、`value`、`source` | 指标值，学生+指标+学期唯一 |
| `sp_tag` | `code`、`name`、`dimension`、`description`、`rule` | 标签定义与规则 JSON |
| `sp_student_tag` | `student_id`、`tag_code`、`term`、`evidence` | 标签结果与依据，按学期隔离 |
| `sp_profile_snapshot` | `student_id`、`term`、`payload` | 按学期保存的画像快照 |

`sp_student` 是读模型：治理模块合并出学生主数据后同步过来，画像模块不负责“一人多号”的归并。

画像模块同时向 M6 数据服务网关注册只读提供方 `student_profile`（字段 `student_id/student_no/class_id/class_name/name/major/org_id/grade`），供 `POST /api/modules/data-services/services/:id/invoke` 按授权范围与脱敏规则对外提供学生基础数据。

## 5. 数据库使用方式

- 运行时使用 MySQL 8.4，不再读写 `data/platform.db`。
- 默认连接串：

  ```text
  mysql://platform:PlatformPass123!@127.0.0.1:3307/student_platform
  ```

- 可以用完整连接串覆盖：

  ```powershell
  $env:PLATFORM_DB_URL = "mysql://platform:密码@127.0.0.1:3307/student_platform"
  ```

  也可以分别设置 `PLATFORM_DB_HOST`、`PLATFORM_DB_PORT`、`PLATFORM_DB_USER`、`PLATFORM_DB_PASSWORD`、`PLATFORM_DB_NAME`。

- `PLATFORM_TEST_DB=1` 时数据库名自动追加 `_test_<pid>_<timestamp>`，每个测试进程使用独立库（同一进程内的所有模块共享该库）；测试数据库由账号自动创建。
- 本地开发账号需要目标库的建表权限；测试账号还需要 `CREATE DATABASE` 权限。生产环境建议预先建好数据库并只授予目标库权限。
- 表名按模块加前缀（`ing_`、`gov_`、`sp_`、`cd_`，M6 使用 `users/roles/services/...`），共用一个 MySQL schema。
- 表使用 InnoDB 和外键约束；启动时执行 `CREATE TABLE IF NOT EXISTS`。目前没有 SQLite 数据迁移，MySQL 是新建 schema。

## 6. 构建与运行

### 6.1 VS Code（Windows）

1. 安装并启用 CMake Tools、C/C++ 扩展。
2. 启动 MySQL 8.4，创建 `student_platform` 库和 `platform` 账号（或设置 `PLATFORM_DB_URL`）。
3. 如果 CMake 找不到 MySQL 头文件，配置 `PLATFORM_MYSQL_ROOT` 指向 MySQL ZIP 解压目录；Windows 下 CMake 会自动尝试 `%LOCALAPPDATA%\Programs\mysql-8.4.13\mysql-8.4.13-winx64`。
4. 打开项目根目录，选择 preset `windows-vs2026`。
5. `F7` 构建，`F5` 运行 `platform_server`（`.vscode/launch.json` 已配置）。
6. CMake Tools 的 Testing 面板或 `ctest --preset windows-vs2026` 跑测试。

如果 Visual Studio 报找不到 `cl.exe` 或 `cmake.exe`，打开 Visual Studio Installer → 修改 → 勾选“使用 C++ 的桌面开发”和“C++ CMake tools for Windows”。

### 6.2 MinGW 备用构建

任何 MinGW-w64 GCC 13+ 都可以构建；`CMakeLists.txt` 会在 MinGW 下静态链接运行库，生成的 exe 不依赖编译器 DLL：

```powershell
cmake -S . -B build/mingw-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug `
      -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ `
      -DPLATFORM_MYSQL_ROOT="C:/path/to/mysql-8.4.13-winx64"
cmake --build build/mingw-debug
ctest --test-dir build/mingw-debug --output-on-failure
.\build\mingw-debug\platform_server.exe 8090
```

MinGW 构建会把 `libmysql.dll`、`libssl-3-x64.dll`、`libcrypto-3-x64.dll` 复制到可执行文件目录。

如果 `ctest` 列表里没有 `http_smoke`，说明 CMake 没找到可用的 Python，可以显式指定：

```powershell
cmake -S . -B build/mingw-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug `
      -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ `
      -DPython3_EXECUTABLE="C:/Users/你的用户名/AppData/Local/Programs/Python/Python314/python.exe"
```

### 6.3 Linux

先安装 MySQL 客户端开发包（例如 Ubuntu 的 `libmysqlclient-dev` 或 `mariadb-devel`），再：

```bash
cmake --preset linux-debug
cmake --build --preset linux-debug
ctest --preset linux-debug
./build/linux-debug/platform_server 8090
```

浏览器打开 <http://127.0.0.1:8090/>。如果 8080 被其它程序占用，就用 8090。

## 7. 演示流程

## 9. 可继续优化的点

1. **真正的调度器**：`schedule_expr` 目前只保存配置，需要后台线程/定时器执行。
2. **权限与脱敏**：接入 M6 的角色、数据范围和脱敏结果；当前画像查询没有鉴权。
3. **PDF 报告**：当前 `report` 返回 HTML；PDF 留到前端/后续迭代。
4. **主数据与指标联动**：目前 `POST /students`、`POST /metrics` 由治理模块或演示脚本同步；正式联调时应由治理模块在合并主数据/重算指标后调用。
5. **导入文件格式**：当前只接收 JSON 数组；CSV/Excel 样例文件导入可以后续补。

## 11. 数据治理模块（M2）

路由前缀：`/api/modules/data-governance`。阶段 4 起从内存 mock 改为 MySQL 落库，代码分层与 M1/M3 一致：
`module.cpp`（路由 + 鉴权）→ `service.cpp`（归并规则、指标口径、跨模块同步）→ `repository.cpp`（`gov_` 表 SQL）。

### 11.1 接口

| 用例 | 方法与路径（相对前缀） | 说明 |
| --- | --- | --- |
| 查看质量规则 | `GET /quality-rules` | 读 `gov_quality_rule`；首次启动写入 3 条种子规则 |
| 新建质量规则 | `POST /quality-rules` | `rule_name`/`rule_type`/`target_field` 必填；重名 409；`level` 只接受 `error/warn/info` |
| 启停质量规则 | `PATCH /quality-rules/:rule_id` | 修改 `enabled` / `level`；规则不存在 404 |
| 查询学生主数据列表 | `GET /student-master` | 返回 `gov_student_master` 全部记录，工作台列表使用 |
| 查询学生主数据 | `GET /student-master/:student_id` | 读 `gov_student_master`；不存在返回 404 |
| 多源归并主数据 | `POST /student-master/merge` | 只有非空字段才覆盖已有值；归并后同步写 M3 的 `sp_student` |
| 指标重算 | `POST /recalculate` | 读 `ing_raw_record`，按 `gov_metric_def` 计算并写 `sp_metric_value`；返回真实任务 ID 与结果 |
| 质量报告 | `GET /quality-report` | 实时统计原始记录数、脏数据数、质量得分、主数据覆盖率 |

归并示例：

```json
{"student_id": "1001", "student_no": "2023001", "name": "张三",
 "major": "软件工程", "class_name": "软工2301", "org_id": "college-cs", "source": "academic-office"}
```

重算示例（`student_ids` 可省略，默认全部主数据学生；`term` 省略时取最新指标口径学期）：

```json
{"term": "2025-2026-1", "student_ids": ["1001", "1002"]}
```

返回：

```json
{
  "task_id": "recalc_12", "status": "finished", "term": "2025-2026-1",
  "student_count": 2, "metric_count": 8,
  "results": [{"student_id": "1001", "student_no": "2023001",
               "metrics": {"score_avg": 90, "score_pass_rate": 100, "credit_total": 5}}]
}
```

### 11.2 表结构

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `gov_quality_rule` | `rule_name`（唯一）、`rule_type`、`target_field`、`level`、`enabled` | 质量规则配置 |
| `gov_student_master` | `student_id`（主键）、`student_no`、`name`、`major`、`class_name`、`org_id`、`status`、`source`、`merged_at` | 多源归并后的学生主数据 |
| `gov_metric_def` | `metric_code`、`name`、`formula`、`weight`、`term`、`version`、`active` | 指标口径，按 `metric_code + term + version` 唯一 |
| `gov_recalc_task` | `term`、`status`、`student_count`、`metric_count`、`created_at`、`finished_at` | 每次重算的真实任务记录 |

种子数据：3 条质量规则、3 名演示学生（`1001/1002/1003`）、4 条指标口径（`score_avg`、`score_pass_rate`、`attendance_rate`、`credit_total`），均用 `INSERT IGNORE`，不会覆盖已有配置。

### 11.3 指标口径

`formula` 只支持固定聚合函数，避免执行任意表达式：

| 写法 | 含义 |
| --- | --- |
| `avg(field)` | 平均值 |
| `sum(field)` | 求和 |
| `count(field)` | 有该字段的记录数 |
| `max(field)` / `min(field)` | 最大/最小值 |
| `pass_rate(field,60)` | 大于等于阈值的百分比，阈值省略时按 60 |
| `count_if(field,lt,60)` | 满足比较条件的记录数（支持 `lt/lte/gt/gte/==/!=`），用于不及格门数 |
| `ratio(field,20)` | 求和后除以固定分母，用于完成率（如学分完成率） |

原始记录通过 `student_id`、`student_no` 或 `学号` 关联到学生；同一学生的两条记录（id 与学号各命中一次）会按记录 ID 去重，不会重复计数。非数字字段值会被跳过。
`sp_metric_value.source` 统一写 `governance`，便于区分手工同步的指标。

### 11.4 权限

新增 `governance.read` / `governance.write`，只授予 `system_admin` 和 `data_admin`，且要求全校数据范围。旧库启动时由 `Store` 的 `grant_permissions` 自动补权限；M2 路由未登录返回 401，学生/辅导员访问返回 403。

### 11.5 跨模块边界

M2 需要写 M3 的 `sp_student` / `sp_metric_value`，统一通过 `student_profile::ProfileRepository` 在 service 层集中写入（复用 M3 的建表与 upsert 语义），路由层不出现跨模块 SQL。

## 12. 学业分析与预警模块（M4）

路由前缀：`/api/modules/academic-alerts`。阶段 5 起从内存单例改为 MySQL 落库，模块详细说明见 [`src/modules/academic_alerts/README.md`](../src/modules/academic_alerts/README.md)。

- 表：`aa_alert_rule`（规则）、`aa_alert_record`（预警，`created_at` 存 epoch）、`aa_intervention`（干预记录）。
- 数据来源：学生读 `sp_student`，指标只读 `sp_metric_value`（由 M2 计算）；`src/modules/academic_alerts/alerts_api.cpp` 的 `metric_bindings()` 负责把规则指标映射到 M2 指标码并换算（`attendance` 百分比 → 0~1）。没有指标值的学生不参与判定。
- 权限：`alert.read` / `alert.write`，辅导员本班、院系本学院、数据/系统管理员全校；配置规则额外要求全校范围。
- 生成幂等：同一学生同一规则存在 `open/claimed` 预警时跳过；认领与处置全部写 `aa_intervention`，重建应用后仍可追溯。
