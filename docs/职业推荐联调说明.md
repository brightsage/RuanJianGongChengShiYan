### 职业推荐联调说明

#### 学生画像模块对接

**当前采用的约定**　画像负责人暂未确认业务字段，本分支先按现有 [C++ 画像仓储](../src/modules/student_profile/repository.hpp) 接入。组员联调时优先核对下面四项，若口径不同，集中修改 [画像适配器](../src/modules/career_recommendation/profile.cpp)

| 核对项 | 当前约定 |
| --- | --- |
| 学号和数据源 | 从 M6 的 `Principal.student_no` 取学号，直接对应 `Student.student_id`。M3 用 `SqliteProfileRepository` 将学生和指标写入同一平台数据库，推荐读取 `find_student`、`list_metrics`、`find_snapshot` |
| 能力标识 | 岗位的 `requirements[].competency_code` 和 `MetricValue.metric_code` 按原值匹配，区分大小写。演示用 `programming`、`databases`，正式岗位维护时应填画像实际产生的指标编码 |
| 量纲和缺失 | `score_100` 和 `%` 接受 0 至 100，值直接使用。 `ratio_1` 接受 0 至 1，乘 100 后使用。未知量纲、越界值和无对应指标都视为缺失。局部缺失贡献为 0，理由中 `student_score` 与 `gap` 为 `null`。选中周期完全没有可用指标时返回 `409` |
| 周期和版本 | 请求可传 `term`。省略时用该学生 `calculated_at` 最新的一条记录所属周期，时间相同用字典序较大的 `term`。时间字段统一用 SQLite 仓储的 UTC `YYYY-MM-DD HH:MM:SS` 格式。版本由周期、有效指标编码／归一值／计算时间和可选的快照 ID／生成时间生成，画像内容变化后产生新推荐记录 |

联调只需准备一名绑定相同学号的 M6 学生、一个周期的指标、一个已发布岗位和一条生效策略。建议先验证编程指标 `0.8 ratio_1`、数据库指标 `40 %`，岗位两项达标线都设为 80，权重分别为 3 和 1，策略权重为 60／40。学生应得到 80.00 分，数据库能力差 40 分。将数据库指标改为 80，再查询应得到 100.00 分和新的推荐 ID，旧 ID 仍显示原快照

#### M6 和共用数据库

- 正式服务和画像仓储使用同一个平台数据库，默认 `data/platform.db`，用 `PLATFORM_DB_PATH` 可指定绝对路径。M6 独立分支曾用 `PLATFORM_DB`，合并后兼容该变量，两个变量同时设置时以 `PLATFORM_DB_PATH` 为准
- 在 `/data-services` 使用 M6 管理账号创建 `career_center` 和 `student`。学生必须绑定组织、班级、学号。进入 `/career` 后分别用这两类账号登录，浏览器携带 `Authorization: Bearer <token>`
- 岗位读取用 `career.jobs.read`，新增和编辑用 `career.jobs.write`，发布和下架用 `career.jobs.publish`，读取和修改策略均用 `career.strategy.write`。这四项要求全校范围。三个学生接口共用 `career.recommendations.read`，推荐理由和反馈还按当前学号校验记录归属
- 岗位、策略写入借用 M6 提供的 SQLite 连接，和 `career.job.create/update/publish/unpublish/republish` 或 `career.strategy.update` 审计同事务提交。审计失败时业务回滚。拒绝和事务内失败由 M6 记审计。可用管理账号从 `GET /api/modules/data-services/audit-logs` 核对动作、结果和变更字段
- 演示服务显式启用 `PLATFORM_CAREER_DEMO=1`，使用独立 `data/career-demo.db`。演示请求有 `X-Career-Demo: 1`，学生请求另带 `X-Career-Demo-Student: demo-1` 或 `demo-2`。正式请求一律从 M6 身份读取学号

#### 推荐、理由和反馈接口

所有路径都加前缀 `/api/modules/career-recommendation`。路径中的 `:id` 是推荐 ID。列表同时返回 `job_id` 供关联岗位

| 请求 | 请求体与结果 |
| --- | --- |
| `POST /recommendations/query` | 可传 `{"term":"2026-2027-1","industry":"信息技术","min_score":75}`，三个字段均可省略。返回 `{term,items:[{id,job_id,title,industry,job_type,score,feedback}]}` |
| `GET /recommendations/:id/reason` | 返回 `id`、`job`、`score`、`term`、`profile_version`、`strategy_version`、`algorithm`、`criteria` 和当前 `feedback`。每项明细含能力标识、达标线、权重、画像分、状态、差距和分数贡献 |
| `PUT /recommendations/:id/feedback` | 提交 `{"choice":"interested","reason":"方向符合"}` 或将 `choice` 改为 `not_interested`。原因必填。返回 `{choice,reason,updated_at}`。相同内容重试保留原时间，修改覆盖原反馈 |

- 只推荐已发布岗位。岗位先按策略行业、岗位类型和请求行业筛选，再按策略与请求中较高的最低分筛选。同分时岗位 ID 较小者在前
- 加权达标按各项达标权重占比算分。加权接近度按画像值与达标线之比算分，每项上限为 1。两项按策略权重合成，最后保留两位小数用于筛选、排序与显示
- 学号、岗位 ID 及版本、策略版本、画像版本相同会复用推荐 ID。岗位修改、下架、策略更新、画像更新之后仍可按旧推荐 ID 查看原理由和原反馈
- 未登录或令牌失效返回 `401`，角色权限不符返回 `403`，不存在或属于其他学生的推荐统一返回 `404`，未配置策略或当前周期没有可用画像返回 `409`，无匹配岗位返回 `200` 和空列表

#### 就业去向数据对接

**当前采用的临时约定**　数据提供方在同一个 `PLATFORM_DB_PATH` 数据库中提供 `cd_outcome_source` 视图。视图每行对应一位毕业生的一次毕业，覆盖该届毕业生名册，包括尚未登记去向的人。数据提供方负责按毕业记录标识去重，并从多次上报中选定一条有效去向。接入时先核对毕业年份、类别映射、行业来源、名册覆盖范围和去重规则，再用同一批脱敏记录对账

| 视图列 | 约定 |
| --- | --- |
| `graduation_year` | SQLite 整数，1900 至 2199，使用实际毕业年份 |
| `outcome_category` | `employed` 就业、`further_study` 升学、`abroad` 出国（境）、`unemployed` 待就业、`other` 其他、`unknown` 未登记。缺失可用 SQL `NULL`，会归入未登记。其他原始编码由数据提供方在视图中映射 |
| `industry` | SQLite 文本，使用毕业生实际就业单位的统一行业名称。只有 `employed` 计入行业统计，缺失用 `NULL`，空串或仅含普通空格也归到未登记行业 |

下面的 SQL 在**测试数据库**中建立脱敏样表，插入 2024 届的三份毕业记录，再建立正式接口使用的视图。真实联调时用组员的来源表替换示例表，在视图中完成字段映射。视图只暴露统计所需的三列

```sql
CREATE TABLE sample_graduates (
    graduation_year INTEGER NOT NULL CHECK (graduation_year BETWEEN 1900 AND 2199),
    graduate_key TEXT NOT NULL,
    outcome_category TEXT CHECK (outcome_category IN
        ('employed', 'further_study', 'abroad', 'unemployed', 'other', 'unknown')),
    industry TEXT,
    PRIMARY KEY (graduation_year, graduate_key)
) STRICT;

INSERT INTO sample_graduates VALUES
    (2024, 'sample-a', 'employed', '信息技术'),
    (2024, 'sample-b', 'employed', NULL),
    (2024, 'sample-c', 'further_study', NULL);

CREATE VIEW cd_outcome_source AS
SELECT graduation_year, outcome_category, industry FROM sample_graduates;
```

- **权限**　需要 `career.outcomes.read` 且范围为全校。新数据库的默认 `career_center` 自带该权限。升级已有数据库后，由系统管理员在 `/data-services` 的角色管理中编辑 `career_center`，在原权限清单中勾选 `career.outcomes.read` 并保存。也可通过 M6 的 `GET /roles` 读取现有角色，然后用 `PUT /roles/career_center` 提交原名称、原范围和追加后的完整权限数组
- **接口**　`GET /api/modules/career-recommendation/outcomes?from_year=2024&to_year=2024`，两端都包含，单独省略某端表示该侧不限。结果的 `outcome_distribution` 按毕业生数计算百分比，`industry_distribution` 按已就业人数计算，未登记行业以 `industry: null` 返回。 `trend` 按毕业年份升序，返回人数、就业占比和该年去向分布。占比保留两位小数
- **对账**　正式模式用就业中心账号打开 `/career`，查询示例的 2024 年，应得到 3 人、就业 2 人（66.67%）、升学 1 人（33.33%），两个就业行业分组各占 50%，趋势只有 2024 年。没有记录的年份范围返回 `200`、零人数和空趋势。视图未接入或所选范围含未映射的类别时返回 `503`。错误年份返回 `400`，无权账号返回 `403`
- **演示**　就业中心视图可直接查询内置样例。默认覆盖 2023 至 2025 届，毕业生 8 人、已就业 4 人。演示结果标明数据来源
